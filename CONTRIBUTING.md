# Участие в разработке OlimpHub

Этот документ задаёт обязательный процесс изменений в OlimpHub. Репозиторий — единственный источник достоверной информации о продукте, коде, архитектуре и принятых решениях.

## Базовое правило

Каждое изменение должно улучшать продукт без скрытого увеличения технического долга. Не удаляйте работающую функциональность и не меняйте публичное поведение без обоснования, тестов, обновления документации и отдельного описания миграции там, где она нужна.

| Приоритет | Ожидание                                                                              |
| --------: | ------------------------------------------------------------------------------------- |
|         1 | Соблюдать границы доменных модулей и не обходить публичные контракты.                 |
|         2 | Реализовывать завершённые пользовательские сценарии, а не демонстрационные прототипы. |
|         3 | Сохранять понятный, доступный и устойчивый UX во всех состояниях интерфейса.          |
|         4 | Проектировать защиту данных и авторизацию до добавления нового действия с данными.    |
|         5 | Добавлять тесты пропорционально риску изменения.                                      |
|         6 | Поддерживать документацию, миграции и журнал решений в актуальном состоянии.          |

## Перед началом работы

Перед изменением изучите `README.md`, [архитектуру](docs/architecture.md), [дорожную карту](docs/roadmap.md) и затрагиваемый модуль. Уточните, кто владеет данными и правилами, какие контракты уже существуют и какие пользовательские сценарии изменение должно сохранить.

Если изменение затрагивает больше одного модуля, добавляет источник данных, меняет модель авторизации, публичный API, схему базы данных или способ развёртывания, сначала создайте или обновите архитектурное решение в `docs/`. Нельзя начинать масштабную реализацию на основе незафиксированных предположений.

## Стандарты реализации

| Область            | Обязательное требование                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| Модульность        | Код домена не зависит от HTTP, ORM, SDK внешних сервисов или конкретных компонентов интерфейса.                           |
| Контракты          | Входные и выходные схемы валидируются на границе; изменение публичного контракта совместимо или версионировано.           |
| Ошибки             | Пользовательские ошибки понятны и не раскрывают внутренние данные; технические ошибки получают контекст в журналировании. |
| Доступность        | Интерактивные элементы доступны с клавиатуры, имеют видимый фокус и понятную текстовую семантику.                         |
| Безопасность       | Авторизация проверяется на сервере; секреты не коммитятся; данные пользователя изолированы по владельцу.                  |
| Производительность | Потенциально тяжёлые операции не выполняются синхронно в запросе без доказанной необходимости.                            |
| Зависимости        | Новая зависимость должна решать конкретную проблему, иметь поддерживаемую лицензию и не дублировать имеющийся инструмент. |

Не оставляйте очевидные `TODO`, пустые обработчики, фиктивные данные в рабочем пути или комментарии, заменяющие реализацию. Если задача объективно выходит за рамки изменения, её необходимо описать как отдельное решение с причиной и границами, а не скрывать в коде.

## Тестирование

После существенного изменения необходимо запускать все доступные проверки проекта. До появления конкретного стека это требование применяется как правило процесса; после создания каркаса единая команда проверки должна запускать линтер, проверку типов, модульные и интеграционные тесты.

| Вид изменения               | Минимальная проверка                                                                       |
| --------------------------- | ------------------------------------------------------------------------------------------ |
| Чистая документация         | Проверка ссылок, структуры Markdown и диффа.                                               |
| Доменное правило            | Модульные тесты на нормальный случай, границы и запрет недопустимого состояния.            |
| Сценарий приложения или API | Интеграционные тесты авторизации, валидации и результата.                                  |
| Интерфейсный поток          | Компонентные/сквозные тесты плюс проверка состояний загрузки, ошибки и пустого результата. |
| Изменение схемы БД          | Миграция с чистой БД и безопасный сценарий обновления существующих данных.                 |
| Адаптер источника           | Контрактные тесты с воспроизводимыми фикстурами и проверка обработки ошибок.               |
| Безопасность или сессии     | Тесты разрешённого и запрещённого доступа, проверка отсутствия секретов в выводе.          |

## Git-процесс

Работа ведётся небольшими тематическими коммитами. Коммит должен содержать завершённую, проверенную единицу ценности: реализацию, необходимые тесты и релевантную документацию.

Сообщения коммитов формулируются в повелительном наклонении и отвечают на вопрос, что меняется. Пример: `docs: define OlimpHub modular architecture`. Не смешивайте рефакторинг, новую функцию и массовое форматирование в одном коммите, если они не являются одним неделимым изменением.

Перед коммитом проверьте:

1. `git diff --check` не сообщает об ошибках пробелов.
2. Рабочая ветка не содержит случайных файлов, секретов, сборочных артефактов или зависимостей, которые должны игнорироваться.
3. Запущены подходящие проверки, а результаты отражены в описании изменения или pull request.
4. Документация обновлена, если изменились поведение, контракт, модель данных, настройка или архитектурное решение.

## Документация и решения

`README.md` описывает назначение проекта, статус и точку входа. В `docs/architecture.md` отражаются долгоживущие архитектурные границы. В `docs/roadmap.md` поддерживается порядок поставки. По мере появления реализации следует добавлять краткие документы для запуска, конфигурации, API, модели данных и развёртывания.

Архитектурное решение документируется до реализации, если его отмена или изменение позднее будет дорогим. Документ должен содержать контекст, выбранный вариант, последствия и критерии пересмотра. Решение не должно пересказывать код; его задача — объяснить, почему код устроен именно так.

## Definition of Done

Изменение считается завершённым только тогда, когда оно соответствует следующей таблице.

| Условие                                                  | Обязательно |
| -------------------------------------------------------- | ----------- |
| Пользовательская или инженерная цель явно сформулирована | Да          |
| Владение модулем и данными определено                    | Да          |
| Реализация не ломает существующий согласованный сценарий | Да          |
| Тесты соответствуют риску изменения и проходят           | Да          |
| Безопасность, доступность и ошибки рассмотрены           | Да          |
| Документация и миграции обновлены при необходимости      | Да          |
| Изменение зафиксировано понятным Git commit              | Да          |

Если любое условие не выполнено, работа остаётся незавершённой и не должна представляться как готовая возможность.
