# Codeforces API: контракт, ограничения и курс интеграции

**Задача backlog:** P0-002  
**Статус:** завершено  
**Дата исследования:** 14 августа 2026  
**Назначение:** техническая основа для будущего адаптера Codeforces и синхронизации профиля

## Вывод

Codeforces API — пригодный первый источник **публичных метаданных** задач, контестов, пользовательского рейтинга и отправок. Он не является полным контентным API: официальный контракт возвращает машинно-читаемые JSON-объекты и задаёт жёсткое ограничение в один запрос за две секунды.[1] Поэтому OlimpHub должен строить интеграцию как медленный, идемпотентный фоновый процесс с локальными снимками, журналом происхождения и понятным состоянием свежести, а не как прокси-запросы из интерфейса.

> Все методы доступны анонимно только для публичных данных. Доступ к пользовательским приватным данным требует API key и secret, а подписанный запрос отклоняется при расхождении времени сервера и параметра `time` более чем на пять минут.[1]

## Официальный транспортный контракт

Каждый вызов отправляется на `https://codeforces.com/api/{methodName}` и возвращает объект с полем `status`: `OK` или `FAILED`. При неудаче причина находится в `comment`; при успехе полезные данные находятся в `result`.[1] Это означает, что HTTP-успех сам по себе не является признаком успешной синхронизации: адаптер обязан валидировать поле `status`, классифицировать `comment` и сохранять диагностическое событие без записи частичных данных как успешных.

| Аспект            | Официальное поведение                                                                       | Требование к OlimpHub                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Лимит             | Не более одного запроса за две секунды; при превышении `FAILED` / `Call limit exceeded`.[1] | Один общий диспетчер на учётные данные/инстанс с минимальным интервалом **≥ 2,2 с**, джиттером и очередью. Нельзя запускать параллельные запросы из разных задач.        |
| Ошибка API        | `FAILED` плюс текстовая причина в `comment`.[1]                                             | Данные не меняются до успешной валидации; причина сохраняется в `ImportRun`, а временные ошибки повторяются с ограниченной экспоненциальной задержкой.                   |
| Язык              | `lang=en` или `lang=ru` выбирает локализованные поля.[1]                                    | Вначале хранить оригинальную локаль и локаль ответа в provenance; не перезаписывать одноязычные поля другой локалью без правила версионирования.                         |
| Анонимный режим   | Только публичные данные.[1]                                                                 | Каталог и привязка публичного handle не требуют секретов. Ключ не вводится в MVP ради данных, доступных анонимно.                                                        |
| Подписанный режим | Нужны `apiKey`, `time` и SHA-512 `apiSig`; подпись включает secret.[1]                      | Если позднее понадобится, ключ и secret находятся только на сервере в менеджере секретов; подпись формируется в изолированном инфраструктурном адаптере и не логируется. |

## Поля, доступные для первичной нормализации

Официальная структура `Problem` содержит внешние идентификаторы `contestId`, `problemsetName` и `index` (часть может отсутствовать), название, тип `PROGRAMMING` или `QUESTION`, необязательные `points` и `rating`, а также список тегов.[3] `ProblemStatistics` содержит `contestId`, `index` и `solvedCount`.[3] Эти поля достаточны для создания ссылки на источник, метаданных сложности и необработанных тегов; они не достаточны для собственной подробной педагогической классификации.

| Объект              | Поля, используемые в MVP                                                                                          | Как хранить                                                                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `Problem`           | `contestId`, `problemsetName`, `index`, `name`, `type`, `points`, `rating`, `tags`                                | Неизменяемая внешняя ссылка плюс версионируемый снимок метаданных. Отсутствующие поля хранятся как неизвестные, а не подменяются значениями. |
| `ProblemStatistics` | `contestId`, `index`, `solvedCount`                                                                               | Отдельный снимок статистики с `observedAt`; это изменяемая телеметрия, а не идентичность задачи.                                             |
| `User`              | `handle`, `rank`, `rating`, `maxRank`, `maxRating`, временные поля                                                | Связь с пользователем OlimpHub и снимок профиля; необязательные личные поля не импортируются без продуктовой необходимости.                  |
| `RatingChange`      | `contestId`, `rank`, `oldRating`, `newRating`, `ratingUpdateTimeSeconds`                                          | Нормализованная история рейтинга, идемпотентная по внешнему событию.                                                                         |
| `Submission`        | `id`, `contestId`, `creationTimeSeconds`, `relativeTimeSeconds`, `problem`, вердикт и язык из полной схемы ответа | Неизменяемая внешняя отправка; исходный код по умолчанию не запрашивается и не хранится.                                                     |

## Решение по синхронизации

### Каталог

Начальный каталоговый импорт запускается вручную или как контролируемое административное задание, а не при пользовательском запросе. Он вызывает `problemset.problems`, проверяет контракт, нормализует внешний ключ и пишет итог только транзакционными пакетами. Для каждой задачи сохраняются `sourceKey`, снимок источника, версия адаптера, время наблюдения и хэш нормализуемых полей. Повторная загрузка с тем же хэшем не создаёт новую запись и не меняет пользовательский прогресс.

Последующие запуски получают новый снимок и сравнивают его с сохранённым хэшем. Новая задача добавляется, изменённая задача создаёт новую версию метаданных, отсутствующая задача не удаляется автоматически: она получает состояние «не наблюдалась в текущем снимке» до отдельной политики ретенции. Это защищает личную историю от временного или частичного ответа источника.

### Профиль и отправки

После того как пользователь явно укажет handle, сервис выполняет `user.info`, нормализует регистр и сохраняет подтверждённый публичный идентификатор. `user.rating` можно получать полностью при первом связывании и повторно с идемпотентным объединением по внешнему конкурсу/времени. `user.status` запрашивается страницами в порядке убывания `id`; сервис обрабатывает небольшой перекрывающийся диапазон последних отправок, объединяет по `submission.id`, останавливается у известного watermark и периодически делает более глубокую сверку.

Повторы сетевых и лимитных ошибок не должны менять watermark. После ограниченного числа попыток задача получает состояние `retryable_failure` с ближайшим временем следующей попытки; пользователь видит «данные не обновлены», а не ложное «нет отправок».

P1-303 реализует текущий безопасный baseline: каталог получает стабильный SHA-256 fingerprint нормализованных метаданных и пропускает запись при неизменном snapshot. Отправки получают страницы по 1000 записей, продолжают обход до сохранённого cursor или исчерпания источника, дедуплицируются уникальным внешним ID и продвигают cursor только после успешной записи всех новых страниц. При ошибке источника cursor не изменяется. Детерминированные тесты подтверждают стабильность fingerprint, монотонность cursor и сценарий с более чем 1000 новыми отправками.

P1-305 добавляет единый in-process coordinator Codeforces. Он сериализует разные вызовы источника с минимальным интервалом 2,2 секунды, объединяет одновременно запущенные одинаковые запросы и кэширует только успешный `problemset.problems` snapshot на пять минут. Ошибка поставщика не попадает в кэш; при следующем запросе выполняется новый вызов. Пагинированные отправки намеренно не кэшируются, чтобы новый verdict был виден во время синхронизации.

P1-311 добавляет сквозные ingestion scenarios без обращения к live API: тест проходит через Codeforces adapter, request coordinator и multi-page cursor collector. Он подтверждает корректные offsets следующей страницы, остановку на durable cursor, отсутствие исходного кода в нормализованной отправке и сохранение retryable provider failure вместо подмены его пустым результатом. Дополнительно одновременные идентичные ingestion-запуски объединяются в одни provider calls, следующая cursor page проходит через минимальный интервал coordinator, а следующий запуск после ошибки выполняет новый запрос вместо чтения failure из кэша.

P1-401 валидирует declared public handle перед сохранением через `user.info`. Адаптер использует каноническое написание имени, сохраняет его нормализованный ключ и не принимает несуществующий/неподтверждённый provider profile как привязку. Такой результат означает только существование публичного профиля: без отдельного подписанного или challenge flow OlimpHub не утверждает, что пользователь владеет Codeforces-аккаунтом.

P1-402 импортирует публичную историю `user.rating` как независимые contest-rating facts. Каждый факт содержит `contestId`, название, место, старый и новый rating и время обновления; таблица имеет уникальность `(userId, contestId, ratedAt)`, поэтому повторная синхронизация обновляет наблюдение, не создавая дубликаты. Sync доступен только после declared public link и показывает пользователю success/error feedback, однако отдельная визуальная rating timeline остаётся задачей P1-406.

P1-404 сопоставляет `user.status` с catalog problem только по устойчивой паре `(sourceId, externalKey)`: для Codeforces это `codeforces` и ключ вида `contestId-index`. Lookup ограничен тем же source до построения map. Если каталог ещё не знает такой ключ, `external_submissions.problemId` остаётся `NULL`; sync не подбирает похожую задачу по названию, URL или тегам и не выполняет destructive merge.

### Минимальный контракт адаптера

P1-301 реализует базовый `ProblemSourceAdapter` в `server/sources/types.ts` и `CodeforcesAdapter` в `server/sources/codeforces.ts`. В текущем контракте доступны `fetchProblemSnapshot` и `fetchSubmissionsPage`; обе операции возвращают типизированный результат `success | retryable_failure | permanent_failure` с точным временем наблюдения. Router использует нормализованные данные адаптера, а не собственный парсер Codeforces. Операции контестов, публичного профиля и рейтинга остаются отдельными последующими расширениями интерфейса.

## Безопасность и приватность

Необходимость в ключах Codeforces отсутствует для базовых публичных сценариев, поэтому в MVP ключи не вводятся. Если в дальнейшем появится легитимная потребность в авторизованном API, `apiKey` и `secret` будут храниться в выделенном секретном хранилище, использоваться только сервером и никогда не попадут в логи, браузер, задания аналитики или таблицы, доступные пользователю.

Тексты ошибок Codeforces считаются недоверенным внешним вводом: они ограничиваются по длине, не рендерятся как HTML и не показываются пользователю без безопасного общего сообщения. Полные ответы API не записываются в обычные логи, потому что они могут включать персональные открытые поля и большие объёмы данных.

## Проверяемые критерии будущей реализации

| Критерий                                                                       | Проверка                                                          |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Ограничитель не запускает два вызова Codeforces чаще одного раза за 2 секунды. | Тест с управляемыми часами и конкурентными заданиями.             |
| `FAILED` не изменяет свежие канонические записи и не продвигает курсор.        | Интеграционный тест на искусственный ответ `Call limit exceeded`. |
